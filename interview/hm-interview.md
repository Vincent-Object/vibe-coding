# 鸿蒙开发者面试指南（面试官用）

> 面试时长：20-30 分钟 | 候选人画像：4-5 年鸿蒙项目经验

---

## 使用说明

这份指南分为 **5 个模块**，每个模块 1-2 个问题，由浅入深。每道题我都给你标注了「听什么」和「红绿灯信号」，你不需要懂技术，只需要对照候选人的回答看是否命中关键词和表达逻辑即可。

---

## 模块一：项目经历摸底（约5分钟）

### 问题 1

**"请介绍一个你主导或深度参与的鸿蒙项目，说说项目背景、你负责的模块，以及最终的落地情况。"**

**你听什么：**

这道题不考技术，考的是他是否**真正做过项目**还是只是了解皮毛。

🟢 好的信号：能说出具体的产品名称或业务场景；能清楚描述自己负责的具体模块（比如"我负责设备发现和配网模块"）；能说出项目的结果（上线了、用户量、解决了什么问题）。

🔴 警惕信号：只说"我做过鸿蒙开发"但说不出具体项目；描述模糊，像是在背介绍而非亲历；把团队成果全部说成自己的，问细节时又支支吾吾。

### 问题 2（追问）

**"在这个项目中，你遇到的最棘手的技术问题是什么？你是怎么定位和解决的？"**

**你听什么：**

考察他的**问题解决能力和思维深度**。

🟢 好的信号：能描述清楚问题的现象（比如"跨设备拉起应用时偶发白屏"）；有一个排查过程（先看日志、再定位到某个接口、最后发现是某个生命周期没处理好）；能说出最终的解决方案和为什么这样解。

🔴 警惕信号：说不出具体问题，只说"遇到一些兼容性问题"；解决方式就是"百度搜了一下"或"问了同事"，没有自己的分析过程。

---

## 模块二：鸿蒙核心概念理解（约5-8分钟）

### 问题 3

**"你能用通俗的话，给我解释一下鸿蒙里 Ability 和 UIAbility 分别是什么吗？它们的关系是什么？"**

**你听什么：**

这是鸿蒙最基础的概念，相当于 Android 的 Activity。一个4-5年经验的人**必须**能清楚解释。

🟢 好的信号：候选人能说出 Ability 是鸿蒙应用的基本组成单元，UIAbility 是带界面的能力组件，用来展示UI和与用户交互；可能还会提到 ExtensionAbility（后台服务类的能力）；能说出一个应用可以有多个 Ability。

🔴 警惕信号：把 Ability 和 Activity 完全混为一谈而说不出区别；完全不知道 UIAbility 这个概念（说明可能还停留在很早期的API版本）；解释得磕磕绊绊，像是在回忆背过的内容。

### 问题 4

**"鸿蒙一直在强调'一次开发，多端部署'，你在实际项目中是怎么实现这一点的？有没有遇到什么坑？"**

**你听什么：**

这是鸿蒙最核心的卖点，也是和 Android/iOS 最大的区别。

🟢 好的信号：能提到**自适应布局**和**响应式布局**；能提到通过资源目录（如针对不同设备类型的 resource 目录）做适配；提到实际项目中的多端场景（手机、平板、手表、智慧屏等）；如果能说出踩过的坑（比如某些组件在不同屏幕尺寸下表现不一致），更加分。

🔴 警惕信号：只是复述口号"一次开发多端部署"但说不出怎么做到的；没有任何多端适配的实际经验；把这个概念和 Flutter 等跨平台框架完全等同。

## 模块三：ArkTS 与 ArkUI 开发能力（约5-8分钟）

### 问题 5

**"你用 ArkTS 开发和以前用 Java/Kotlin/TypeScript 开发相比，最大的不同体验是什么？有哪些让你觉得好用或者不好用的地方？"**

**你听什么：**

ArkTS 是鸿蒙的主力开发语言。这题考的是**实际上手经验**，而不是理论知识。

🟢 好的信号：能说出 ArkTS 是基于 TypeScript 扩展的，但做了一些限制（比如不允许动态类型）；能提到声明式 UI 的开发范式（类似 SwiftUI 或 Compose 的写法）；能说出好用的地方和不好用的地方都有自己的亲身感受，比如"状态管理用装饰器很方便但调试不太好排查"。

🔴 警惕信号：说不清 ArkTS 和 TypeScript 的区别；没有任何使用体感，像是只看过文档；完全不提声明式UI，说明可能没有真正用 ArkUI 开发过界面。

### 问题 6

**"在鸿蒙中，你用过哪些状态管理的装饰器？比如 @State、@Prop、@Link 这些，它们之间的区别是什么？在什么场景下用哪个？"**

**你听什么：**

这是日常开发中高频使用的知识，相当于考一个前端开发懂不懂 React 的 state 和 props。

🟢 好的信号：能说出 **@State** 是组件内部的状态，数据变了UI自动刷新；**@Prop** 是父组件传给子组件的**单向**数据；**@Link** 是父子组件之间的**双向**绑定；可能还会提到 **@Provide/@Consume** 用于跨层级传递、**@Observed/@ObjectLink** 用于嵌套对象的监听；能结合实际场景举例。

🔴 警惕信号：完全分不清这几个装饰器的区别；只知道 @State 不知道其他的；没有在实际场景中使用过。

---

## 模块四：分布式能力与实战（约5分钟）

### 问题 7

**"鸿蒙的分布式能力是它的一大特色。你能说说你在项目中用过哪些分布式相关的能力吗？比如分布式数据管理、跨设备流转这些。"**

**你听什么：**

分布式是鸿蒙区别于其他系统的核心竞争力，4-5年经验的人应该有实际接触。

🟢 好的信号：能提到具体用过的能力，如**分布式数据库**（跨设备同步数据）、**跨设备迁移/流转**（比如手机上看视频流转到智慧屏继续看）、**分布式软总线**等；能描述一个实际业务场景；能说出开发过程中的注意事项（比如设备需要登录同一华为账号、需要在同一局域网等前提条件）。

🔴 警惕信号：只知道概念，没有任何实际使用经验；把分布式能力和普通的网络请求搞混；完全说不出任何分布式相关的内容。

**备注给你：** 如果候选人说他做的项目确实没有涉及分布式场景（比如只做了一个单设备的工具类App），这是可以接受的，但他至少应该能说出**原理层面**的理解。

---

## 模块五：工程化与协作（约5分钟）

### 问题 8

**"你们团队日常开发用的是什么IDE和构建工具？项目是怎么做模块化管理的？"**

**你听什么：**

考察他是否真的在团队中做过鸿蒙项目。

🟢 好的信号：能说出 **DevEco Studio**（鸿蒙官方IDE）；提到构建工具用的是 **hvigor**；能描述项目的模块化方案，比如用 **HAP**（主模块）和 **HSP/HAR**（共享模块/静态库）做模块拆分；能说出团队协作的一些工程实践。

🔴 警惕信号：说不出 DevEco Studio 的名字；不知道 HAP、HSP、HAR 这些概念；对工程结构完全没概念。

### 问题 9（收尾题）

**"如果现在让你从零搭建一个鸿蒙项目的技术架构，你会怎么规划？你会选用哪些技术方案和第三方库？"**

**你听什么：**

这道题考的是**架构能力和技术视野**，是区分"普通开发者"和"高级开发者"的分水线。

🟢 好的信号：有清晰的分层思路（比如UI层、业务逻辑层、数据层）；能提到网络框架的选型、状态管理的方案、路由方案等；了解鸿蒙生态当前的第三方库情况；能提到自动化测试、CI/CD 等工程化考量。

🔴 警惕信号：完全没有架构思维，只说"按照官方文档来"；不知道鸿蒙生态有哪些可用的第三方库；只关注写页面，不考虑工程化。

## 附加模块：DFX 与问题定位能力（约5-10分钟，选问）

> **模块说明：** 你们团队日常处理用户 VOD 和 DFX 问题，这些题目考察候选人面对线上问题时的排查思路和工具使用能力。可以根据时间选 2-3 题来问。

---

### 附加题 1（入门）

**"你知道鸿蒙里的 DFX 是什么吗？你在日常开发或维护中接触过 DFX 的哪些子领域？"**

**你听什么：**

先摸底他对 DFX 这个体系有没有整体认知。

🟢 好的信号：能说出 DFX 是 Design for X 的缩写，是一套面向质量保障的设计体系；能提到其中的具体子领域，比如 **DFR（可靠性）**、**DFT（可测试性）**、**DFS（可维护性）**、**DFP（性能）** 等；能结合自己的工作说出接触过哪些，比如"我主要接触的是日志和故障定位这块"。

🔴 警惕信号：完全没听过 DFX 这个概念；把 DFX 和某个具体工具搞混；只知道名词但说不出任何实际内容。

---

### 附加题 2（核心重点题）

**"假设现在有一个用户反馈：'某个页面打开后就闪退了'，你拿到这个问题后，会怎么一步步去排查和定位？"**

**你听什么：**

这道题**最重要**，直接模拟你们团队日常的 VOD 处理场景。不需要他说出标准答案，重点看他有没有**结构化的排查思路**。

🟢 好的信号（按步骤）：

1. **先收集信息** — 他会先问或先看：设备型号、系统版本、复现路径、是必现还是偶现
2. **看日志** — 提到去抓 **HiLog** 日志，或通过 **FaultLogger**（故障日志框架）拿到崩溃堆栈信息
3. **分析堆栈** — 根据崩溃堆栈定位到具体的代码文件和行号，分析是空指针、数组越界，还是生命周期问题
4. **尝试复现** — 在本地用 DevEco Studio 搭建相同环境复现问题
5. **修复验证** — 修完后做回归测试，确认不影响其他功能

如果候选人还能提到：区分是**应用层崩溃**还是**系统层崩溃**、会先看 **crash 类型**（比如 JS crash 还是 native crash），那说明经验非常丰富。

🔴 警惕信号：没有排查步骤，上来就说"看代码"；不知道 HiLog 或 FaultLogger；从没处理过线上崩溃类问题。

---

### 附加题 3（日志与追踪）

**"你在鸿蒙开发中用过哪些日志和追踪工具？HiLog、HiTrace、HiAppEvent 这些你了解多少？"**

**你听什么：**

这些是鸿蒙 DFX 体系下的核心工具链，也是你们团队日常打交道的东西。

🟢 好的信号：

- **HiLog** — 能说出这是鸿蒙的日志系统，用来打印和查看运行时日志，类似 Android 的 Logcat；能提到日志分级（DEBUG、INFO、WARN、ERROR、FATAL）
- **HiTrace** — 能说出这是做分布式/跨设备调用链追踪的工具，用来串联一次完整请求在不同设备和进程间的调用链路
- **HiAppEvent** — 能说出这是应用事件打点框架，用来采集崩溃事件、卡顿事件、资源泄漏等信息，可以用于线上问题的监控和回捞

如果能说出这些工具在实际工作中怎么配合使用的，就更好了。

🔴 警惕信号：一个都不知道；把 HiLog 和 console.log 等同，看不出有过实际使用。

---

### 附加题 4（性能与卡顿）

**"如果用户反馈'你们的应用用起来很卡'，你会从哪些方向去排查？"**

**你听什么：**

卡顿问题在 VOD 中非常常见，考察候选人有没有性能优化的意识和手段。

🟢 好的信号（提到以下方向越多越好）：

- **UI 线程阻塞** — 主线程有耗时操作（网络请求、大量计算放在了UI线程）
- **组件过度渲染** — 状态变化导致不必要的UI重新绘制（会提到 ArkUI 的状态管理不当导致冗余刷新）
- **内存问题** — 内存泄漏导致 GC 频繁
- **工具使用** — 提到用 DevEco Studio 的 **Profiler** 工具来分析 CPU、内存、帧率等指标；或提到 **HiDumper** 抓取系统信息
- **列表优化** — 如果涉及长列表，会提到 **LazyForEach**（懒加载）来优化

🔴 警惕信号：只说"可能是手机配置低"；没有任何排查工具的概念；对性能优化完全没有方向。

---

### 附加题 5（稳定性与容错）

**"在你的经验中，鸿蒙应用中最常见的崩溃原因有哪些？你在开发中是怎么预防这类问题的？"**

**你听什么：**

这题考察候选人有没有**防御性编程**的意识，以及对常见坑的积累。

🟢 好的信号：能列举常见崩溃原因，比如空指针/undefined 访问、异步回调中的生命周期错误（页面已销毁但回调还在执行）、跨设备通信超时未处理、资源未释放等；在预防方面能提到：做好空值判断和异常捕获、在 **aboutToDisappear** 生命周期里做清理、添加全局的异常兜底机制、通过代码审查和自动化测试来减少问题。

🔴 警惕信号：说不出常见的崩溃类型；没有预防意识，只是"出了问题再修"。

## 附加模块的使用建议

| 场景 | 建议选哪几道 |
|---|---|
| 时间充裕（还剩10分钟） | 附加题 2 + 附加题 4（排查能力 + 性能意识） |
| 时间紧张（还剩5分钟） | 只问**附加题 2**（这道最能区分能力高低） |
| 候选人前面表现很好，想进一步拔高 | 附加题 3 + 附加题 5（工具链深度 + 工程意识） |
| 候选人前面表现一般，想给个翻盘机会 | 附加题 1 + 附加题 2（从基础概念到实操） |

---

## 附加模块的综合评判标准

**核心判断逻辑：** 你们团队需要的是能独立处理线上问题的人，所以最关键的能力是——**拿到一个模糊的用户反馈，能不能自己拆解成技术问题，然后有条理地定位和解决。**

- 如果候选人在附加题 2 和 4 上回答得好，哪怕前面基础题有些不足，也值得考虑，因为这说明他有很强的实战排查能力
- 如果候选人前面基础题全答得漂亮，但附加题里完全没有排查思路，那要谨慎——他可能更擅长写新功能，但未必适合你们以维护和问题定位为主的团队

## 面试节奏建议

| 时间段 | 内容 | 目的 |
|---|---|---|
| 前5分钟 | 模块一（项目经历） | 暖场 + 验证真实性 |
| 5-13分钟 | 模块二（核心概念） | 验证基础功底 |
| 13-21分钟 | 模块三（开发能力） | 验证实际编码水平 |
| 21-26分钟 | 模块四（分布式） | 考察深度能力 |
| 26-30分钟 | 模块五（工程化） | 考察综合素养 |

## 面试中的万能追问句式

当你听不懂候选人的技术回答但又想判断深度时，可以用这几句追问：

1. **"你能举一个你项目中的具体例子吗？"** — 有真实经验的人一定能举出来
2. **"如果不这样做，会有什么后果？"** — 考察他是否理解技术选择背后的原因
3. **"你觉得这块还有什么可以改进的地方？"** — 考察反思能力和成长性
4. **"这个方案上线后有没有出过问题？你怎么处理的？"** — 进一步验证真实性

祝面试顺利！
